# Soroban Authorization Signing Route

## Overview

This document describes the Soroban authorization signing route implementation that allows the server to sign authorization entries with a server key, with validation against an allowlist of contracts and methods.

## Implementation

### Route Handler
**Location:** `routes-d/routes/soroban.auth.sign.ts`

**Endpoint:** `POST /soroban/auth/sign`

**Purpose:** Signs a Soroban authorization entry with the server key after validating the contract and method against an allowlist.

### Request Format

```json
{
  "contractId": "CAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAD2KM",
  "method": "transfer",
  "args": ["arg1", "arg2"],  // optional
  "nonce": "12345"            // optional
}
```

### Response Format

#### Success (200 OK)
```json
{
  "success": true,
  "data": {
    "contractId": "CAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAD2KM",
    "method": "transfer",
    "signature": "base64-encoded-signature",
    "signedAt": "2026-07-26T00:00:00.000Z"
  }
}
```

#### Error Responses

- **400 Bad Request** - Missing or invalid required fields
  - `MISSING_CONTRACT_ID` - contractId is missing or not a non-empty string
  - `MISSING_METHOD` - method is missing or not a non-empty string

- **403 Forbidden** - Authorization validation failed
  - `UNAUTHORIZED_CONTRACT` - Contract not in allowlist
  - `UNAUTHORIZED_METHOD` - Method not allowed for this contract

## Contract Allowlist

The following contracts and their permitted methods are currently authorized:

| Contract ID | Allowed Methods |
|-------------|----------------|
| `CAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAD2KM` | `transfer`, `approve`, `balance` |
| `CBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB` | `swap`, `add_liquidity`, `remove_liquidity` |
| `CCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCCC` | `mint`, `burn` |

## Signature Generation

The signature is generated by:
1. Creating a payload object containing:
   - `contractId`
   - `method`
   - `args` (default: empty array)
   - `nonce` (default: empty string)
   - `serverKey`
2. JSON stringifying the payload
3. Base64 encoding the result

**Note:** This is a mock implementation. In production, this should use proper cryptographic signing with the Stellar SDK.

## Security Considerations

1. **Allowlist Enforcement:** All signing requests are validated against a strict allowlist of contracts and methods
2. **Input Validation:** All required fields are validated for type and non-empty values
3. **Authorization Rejection:** Unauthorized requests receive 403 Forbidden responses
4. **Server Key Protection:** The server key is not exposed in responses (only included in the signature payload)
